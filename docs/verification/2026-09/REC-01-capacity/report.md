# REC-01容量立项评估

2026-09-19。结论：撤回“达到上限自动停录”开发任务，当前不作为产品需求。用户明确训练最长两年，要求先测量再立项。已停止REC-HARDEN-2后台进程；停止后工作树干净，无该任务代码需回滚。存储重试修复e33e73f已验证，独立保留。

## 测量对象与方法

当前录制草稿：engine每批发放1040根K线；推进完成时一份chart=null检查点，图表加载完成时一份完整检查点，随后capture再存一份完整检查点。每个checkpoint重复内嵌bars。数据使用Journey冻结600519样本，2024-09-18～2026-09-16共484次推进；原文件哈希与结果见[result.json](result.json)。

可复现命令：`node node_modules/tsx/dist/cli.mjs scripts/assess-recording-size.ts <冻结sh600519.day路径> <结果json路径>`。本次退出码0。脚本[assess-recording-size.ts](../../../../scripts/assess-recording-size.ts)只读样本；使用现有Recorder及exportRecording，存储为空实现，不访问个人SQLite或写TDX。

实际探针使用原始价格、空持仓、不交易、不绘图、不切周期：120次推进产生480条事件、361个检查点，JSON为27.45MiB。现有exportRecording报错：`导出大小 28784972 字节超过上限 26214400 字节（25MiB）`。这是当前数据结构在合法操作量下的导出失败，不是磁盘满的证据。

按真实样本逐日序列化计算，两年每步两份图表副本仅bars约109.17MiB；每步仅一份也约54.58MiB。单纯推进的检查点约1453，未触及2000个上限，事件约1936，远低于50000。因此不能以“录制很长”笼统断言所有限制都会触发。

## 判断与边界

- 两年训练范围有界，但草稿把每次操作的整份历史行情重复存入；问题主要来自表示方式与人为25MiB限制，不直接支持增加自动停录。
- 优先比较检查点去重、相同行情内容引用、合理导出限制等方案，再确定最小修正。正常两年训练应能完成录制和分享，不以停录替代支持。
- 本样本按raw模式，累计见过1524根独立日线，仅约0.165MiB。这个数只说明重复空间：不能直接当作forward模式最终文件大小。前复权跨基准、周月聚合及用户图形必须保留当时实际观察到的版本，不能合并后前窥未来。
- 未运行浏览器长场Journey，未测IndexedDB写入、内存峰值或加载性能；两年109.17MiB是结构测算，27.45MiB导出失败是实际录制器探针结果，分别报告。

后续立项需给出正常两年场景的文件体积/保存耗时/导入回放证据和方案取舍；不得自动恢复已撤回的停录任务。当前全功能验收仍由REC-01跟踪。
