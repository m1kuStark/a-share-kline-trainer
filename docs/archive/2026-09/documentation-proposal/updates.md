# 更新、状态与证据协议

状态：提案。上级入口：[文档架构](README.md)。目标是让更新成为任务交付的一部分，同时减少重复写入与全局文件冲突。

## 随改动更新

| 发生什么变化 | 实现者必须维护 | 集成者维护 |
|---|---|---|
| 产品行为、边界或验收要求变化 | 对应spec、任务卡、回归映射；必要时新决策 | 变更范围审查，阶段卡及摘要 |
| API、数据格式、模块职责变化 | 对应合约/模块主题页；必要时局部AGENTS | 跨模块入口与依赖审查 |
| 新增/搬移/删除模块或正文 | 最近一级索引、入链与出链 | 全仓链接/路由检查 |
| 纯实现调整、行为不变 | 任务卡中的文档影响判断；失真的实现说明仍要改 | 审查判断理由，不强迫改无关spec |
| 修复bug | 回归测试、任务卡；必要时更新规则与故障说明 | 验证证据及闭环状态 |
| 完成一次测试/视觉排查 | 追加该次验证记录，关联任务 | 候选验证与主代理视觉责任 |
| 合并、返修、回滚 | 补任务交接或返修信息 | 更新集成引用与派生状态 |
| 用户作出阶段验收决定 | 记录决定的来源、范围与对象 | 阶段卡引用；不能从测试结果推断 |
| 任务中断或交接 | 下一步、阻塞、未提交改动、已运行检查 | 重新派工时核对适用基线 |

更新粒度是有意义的工作检查点：确定任务范围、完成一个可验证行为、交接/结束、提交候选、集成验收。不用每运行一条命令就改文档；也不能把全部更新拖到发布前补写。

代码、测试与受影响的规格/实现说明应一起提交。任务只改内部实现且文档仍准确时，记录简短 `docs_impact: none` 和理由，不为满足检查器制造无意义的日期修改。

## 任务卡为工作状态来源

任务路径保持稳定，如 `work-items/tasks/DATA-01.md`。关闭后通过索引过滤，不在 active/done/archive 之间反复搬文件。数量增大时按ID前缀或时期分目录，并维护稳定ID映射。

建议小型结构化卡头；下方只保留范围、验收条件、当前问题和下一步：

```yaml
id: DATA-01
milestone: R1
owner: data-worker
state: active
base_commit: <开发基础SHA>
allowed_paths: [server/src/data/**, server/test/data-refresh.test.ts]
depends_on: []
docs_impact:
  update: [server/src/data/docs/publication.md]
  reason: 发布事务边界改变
verification_refs: []
integration_ref: null
acceptance_ref: null
next_action: 复现目录变更后权息失败
```

`state` 可用 planned/active/blocked/review/closed/cancelled。它表示工作流位置，不直接等同于产品完成。状态页面分别展示实现、自测、集成、视觉、用户验收五个维度；无法从记录确定时显示“未记录/证据不匹配”。

任务完成的具体闸门由所属阶段决定。当前 M3 不要求用户逐工具确认；整体验收仍由用户决定，不能借新文档流程增加逐任务审批。

## 验证记录必须绑定对象

测试记录放 `verification/YYYY-MM/<record-id>/`，至少保存命令、退出码、结果、测试对象SHA、是否脏工作树、环境及必要数据指纹。截图、原始失败日志、重试与最终结果保留关联，不用最终通过覆盖首次失败。

`record-id` 使用任务ID＋时间＋短随机后缀，避免两个工作副本写同一路径。可标记记录类型：test-run、manual-ui、user-acceptance、audit。用户验收记录应包含准确范围、来源引用与日期；自动化不能自己填写“用户已验收”。

提交与报告存在先后关系，建议明确处理：

1. 形成含代码、测试、受影响正文的提交 C。
2. 验证 C，记录 `tested_commit: C`，得到证据 R。
3. 后续文档提交 E 收录 R 和任务卡引用；不要 amend C 后继续沿用旧SHA的通过声明。
4. E 若只改报告、索引和任务元信息，可按明确的文档变更规则继承 C 的运行结果，同时单独检查文档。E 若改源码、构建配置、测试或执行门禁，就重测相关对象。

该继承规则须在实施时写入门禁白名单并审查，不能把任何扩展名为md的变更都视作无运行影响。提交前只能验证脏工作树时，保存文件指纹和差异清单，标为工作树自测；正式候选仍需明确绑定提交。

## 状态页的更新权

worker 只更新自己的任务卡、领域正文和验证记录。不同 worker 不修改同一份全局进度，也不把自己的分支/数据库状态写成全项目现状。

`docs/status.md` 展示：当前阶段与验收边界、进行中/阻塞任务、已集成基线、最近有效证据、下一步。测试数量引用对应记录；“当前目录”交给索引；单次审查的Git状态与长原因放审查报告。

第一步可由集成人从源记录人工汇总，禁止增加第二份状态表。任务卡格式稳定后，再把 status 和大目录清单生成为确定性视图。生成区标明来源，不允许手改；计划优先级等人工字段放任务/阶段卡，不能暗藏在生成页里。

汇总按任务依赖、候选SHA和证据类型匹配，不能按“时间最近的报告”选择。证据过期、引用缺失或回滚后没有新验证时，应显示未知或待验证；阶段 readiness 与用户 accepted 必须分开。

## 检查与强制机制

建议分批增加以下命令，**当前尚不存在**：

| 命令 | 职责 |
|---|---|
| `npm run docs:check` | 相对链接/锚点、ID唯一、元信息、提案/历史标识、长度警示、规范文件名 |
| `npm run docs:impact -- --base <sha>` | 根据diff找受影响模块，要求任务声明对应正文更新或无影响理由；覆盖tracked改动，开发预检另查untracked |
| `npm run docs:status` | 从任务/阶段卡及证据生成状态摘要；初期可暂不实现 |
| `npm run docs:status -- --check` | 检查已生成摘要是否与源记录一致，不静默重写 |

规则来源优先使用模块索引和任务声明。确需机器读取时只给模块README增加简单 `source_paths`、`canonical_docs` 元信息，不再手工维护一份内容相同的全局路径映射表。

检查器可以验证记录存在、SHA可解析、字段和值合法、链接和生成结果一致；不能判断文字是否真实、测试是否充分、用户是否同意。缺关键来源应阻止宣称完成，文档准确性仍由审查承担。

本地检查方便早发现，真正的合并约束要接入统一候选验收命令或CI必需检查；单靠AGENTS/hook不提供强制保证。文档要求不得悄悄降低现有全量Journey、主代理视觉验收和用户阶段验收门槛。
