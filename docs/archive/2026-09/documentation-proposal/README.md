# 目录与文档管理架构

状态：**设计提案，尚未迁移目录或启用规则**。日期：2026-09-17。

目标：Agent 能从任务定位到必要规则和证据；文档随开发更新；长期积累的记录不挤占日常上下文。

## 设计结论

采用“根级导航、模块就近说明、事实单一归属、状态按记录汇总”的结构。

- `AGENTS.md` 写该范围必须遵守的工作规则；只在职责或约束发生变化的边界设置。
- `README.md` 是目录索引，告诉读者这里有什么、何时读、下一步去哪。
- 主题正文独立成页，规格、实现、任务、证据、历史分别存放。
- 单任务状态记录在任务卡，实际验证结果记录在验收证据；项目状态页汇总引用两者。
- 更新责任跟随改动，合并时检查链接、证据和文档影响，不能只依赖 Agent 记得同步。

统一使用大写 `AGENTS.md`；同一目录不另建 `agents.md`。目录导航统一使用 `README.md`，不再维护一份内容相同的 `INDEX.md`。

## 当前依据

本轮盘点：工程入口及 docs 下共 28 份 Markdown；只有根级 AGENTS 与 README，没有模块级文档入口。`changelog.md` 约 1.55 万字符、57 行，`architecture.md` 约 8473 字符、119 行，`testing.md` 约 8090 字符、141 行。长段落让“少于多少行”的限制失效。

此前新增的 [status.md](../../../status.md) 已成为状态入口，但其中目录图、Git 审查快照和本轮日志仍可继续分开。该页的分支和未提交数量描述某次审查，不应让不同 worktree 的 worker 反复覆盖它。

本提案细化 [架构与并行开发建议](../../../ai/architecture-parallel-proposal.md) 的文档部分，不改变当前产品规则、测试门禁或阶段验收安排。

## 落地边界

第一批只增加有价值的入口、搬分现有文档并修复链接，保留业务代码位置与历史证据。任务状态汇总和 docs 检查随后分批加入。目标树中的新目录按实际内容创建，不预建空目录，不给每个小文件配一份说明。

是否成功以三项结果判断：局部任务能找到正确规则；任务交付时相关状态和正文同步；过期或缺失证据能被识别。文件数量减少不是唯一指标。
