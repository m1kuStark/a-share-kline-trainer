# Bug Failure Pattern 分析与自动化防御设计

> 2026-09-06。依据：M1~M3 全部验收反馈、AGENTS.md 更新日志、本会话全部修复记录。
> 目的：回答两个问题——①历史上哪几类 bug 占用了大部分开发精力；②为什么这些 bug 是由用户而不是由自动化测试发现。并给出 journey 自动化与回归网的设计。

---

## 一、Bug 全量清单与 Failure Pattern 统计

对 M1~M3 全部 33 项技术缺陷/修复逐一归类（UX 调优与口径变更不计入）：

### Pattern A：第三方库（klinecharts）内部行为与预期不符 —— 9 项 ≈ 27%

| Bug | 根因 |
|---|---|
| VOL 柱色绿涨红跌 | 库默认国际惯例，未做国内适配审查 |
| 阴线包红边 | borderColor/wickColor 与填充色不同步（部分覆盖时库默认色泄漏） |
| 最新价线配色不生效 | `line.color` 是死键，方向色由 `priceMark.last.upColor` 系计算 |
| 最新价线涨跌色（二次） | 库按 compareRule 相对前收取色，三键从未覆盖 |
| MACD 柱宽为库默认 | bar 图元宽度可由 attrs.width 覆盖（读源码才发现） |
| MACD 最大化命中判定错误 | getSize 的 height 是权重不是像素 |
| B/S 字母不居中 | drawText 强制左上对齐，attrs 对齐被忽略 |
| 缩放下限静默钳制 | barSpaceLimit.max=50 超限 setBarSpace 被静默忽略 |
| getSize bounding right/bottom 恒 0 | 只能 left+width/top+height |
| setZoomEnabled 连程序化缩放一起禁用 | 需改用 setBarSpace+scrollToDataIndex |
| forward 前插自锚定 | 额外补偿滚动引发视图塌缩+加载风暴 |

### Pattern B：多手势/多模式叠加的交互状态缺陷 —— 11 项 ≈ 33%

| Bug | 根因 |
|---|---|
| 框选 offsetX 跳变 | event.offsetX 跨子元素跳变，未用 clientX+window 级监听 |
| 框选越界侵入控制台 | 未按图表宿主钳制 |
| 框选纵向漂移 | 价格轴拖拽把手动模式纵轴冻结，框选缩放前未恢复自动适配 |
| 轴拖拽缩放中断 | 库按 widget 名称路由拖拽，指针移出轴即停止分发 |
| 框选纵向叠加 | 主图拖拽对手动模式纵轴无门控地纵向平移值域 |
| 按画线整图平移 | 我方 7px 命中门限与库内 2px figure 命中的落差带 |
| 中键纵向平移失效 | 自动模式纵轴不记录值域基准（未强制手动模式） |
| 中键按画线拖画线 | 中键合成按下未屏蔽画线拖拽（功能重叠） |
| 中键松键状态残留 | 库 mouseup 只认左键，滚动状态未清理 |
| 射线延伸段无法选中 | 命中几何按两端点线段判定，未按图元覆盖范围延伸 |
| 画线延伸段框选漏选 | 同上（框选相交判定沿用未延伸几何） |

### Pattern C：视觉/主题/精度一致性 —— 4 项 ≈ 12%

| Bug | 根因 |
|---|---|
| 深色主题 topbar 漏网 | 主题覆盖块未遍历全部视图类名 |
| 编辑前后虚线段长不一致 | dashedValue [6,4] 与库默认 [4,4] 两处常量未统一 |
| 端点价位长浮点回显 | 未按价格精度（两位小数）取整 |
| 颜色点击区溢出 | label 包裹 input 的原生行为 |

### Pattern D：数据/状态映射与接线 —— 5 项 ≈ 15%

| Bug | 根因 |
|---|---|
| B/S 跨除权日错位 | 复权基准滚动后，标记未换算到图表空间 |
| 月 K 时间戳 NaN | YYYY-MM 拼接缺 -01 |
| toK 丢 date 字段 | before 参数恒 undefined，请求退化为反复前插 |
| 盲训忘传 :blind | 新 prop 接线遗漏（截图抓现行才定位） |
| 训练中 500 | 旧库缺 market 列的迁移遗漏 |

### Pattern E：API/错误处理契约 —— 2 项 ≈ 6%

| Bug | 根因 |
|---|---|
| Bad Request 吞真实错误 | 唯一未包 try/catch 的路由 + Fastify 兜底 |
| 空表单原样提交 | 客户端校验缺失 |

### 结论

**A（库行为 27%）+ B（交互状态 33%）合计 60%**，是占用绝大部分开发精力的两类。它们的共同特征：

- **A 类**：全部无法从库的公开文档预知，只能读绘制源码或真实使用后发现。库版本钉定 10.0.3，升级即全部失效风险。
- **B 类**：全部发生在**状态组合**里——"轴手动模式之后做框选""画线模式之后按中键""框选之后按 Delete"。单一功能的测试永远踩不到，只有真实用户自由操作才会遍历组合空间。

## 二、为什么这些 bug 是由用户发现的

五个结构性原因，按重要性排序：

1. **验证输入与用户输入不同构**。我用于验证的事件是 `dispatchEvent` 合成事件，它不触发库的真实事件链路（受信任事件、焦点、CDP 输入管线的差异），导致：合成右键触发不了 figure 命中链路、合成拖拽的坐标语义漂移、部分交互根本无法自动化复现。用户用真实鼠标键盘，走的是另一条我覆盖不到的路径。
2. **视觉回归零断言**。截图只作为人工证据存档，从未做像素/结构对比。A 类和 C 类 bug（配色、段长、对齐、柱宽）全部是"看一眼就知道"的偏差，却没有任何自动化眼睛。
3. **状态组合矩阵未遍历**。B 类 bug 全部是"操作 A 之后做操作 B"的组合。我的验证走确定性单路径，用户自由操作天然遍历组合空间。
4. **契约测试滞后于实现**。frontend-contract 的正则断言全部是修完 bug 后补的"已知坑快照"——它们成功防住了已修复项的回潮，但对未知坑零防御。
5. **单功能验收闸门把首次回归推迟给用户**。每个功能单元开发→测试→停机提验的设计（用户拍板）本身正确，但闸门之前缺少一张"已知 failure pattern 的自动回归网"，导致用户成为每个新功能的第一道人工回归。

## 三、最长用户 Journey 的自动化流程设计

最长手册路径＝**训练闭环 + 画线全生命周期 + 交互矩阵 + 主题切换**。设计为 Playwright 真实事件驱动的 journey 套件（关键：Playwright 经 CDP 派发的是**受信任事件**，与用户输入同构，可触发库的全部真实链路——这是与此前合成事件验证的本质区别）。

### Journey 脚本结构（e2e/journey.spec.ts，npm run journey）

```
第 1 幕 训练闭环
  打开首页 → 搜索股票 → 选档/日期/资金 → 创建训练
  断言：训练头部（名称/代码/起始日）、四区域布局、图例、工具条
第 2 幕 画线全生命周期（逐工具）
  线段 → 射线 → 直线 →（后续水平线系…）
  每工具：真实点击绘制 → 断言 overlay 计数+1（测试钩子）→ 拖动端点/整线
  → 右键编辑面板（改色/粗细/样式/价位）→ 确定 → 断言样式生效 → Delete → 断言归零
第 3 幕 交互矩阵（Pattern B 的组合遍历）
  轴拖拽（进入手动模式）→ 框选（断言：不纵向叠加、画线不整体移动）
  轴拖拽中断场景（轴上起拖移入主图，断言：缩放持续）
  中键平移（断言：横向平移+纵向平移、松键后自由移动不再平移）
  按画线拖拽（断言：只动画线、K 线不动）
第 4 幕 多选
  多选模式开关 → 框选三条（断言：全选中、根数不变）
  Ctrl+点选累加/移除 → Delete 批量 → 断言归零
  右键编辑划线（N）→ 选项卡面板 → 逐标签编辑 → 确定 → 断言批量生效
第 5 幕 交易与周期
  B 买入 → 断言 B 标记/成本线 → Space 推进 → 断言日期前进
  S 卖出 → 周期切换 日/周/月（断言画线锚定不漂移）→ 提前结算 → 结算面板
第 6 幕 主题
  切换浅色 → 断言 body.dark 移除 + 截图 → 切回深色 + 截图
```

### 基础设施需求

1. devDependency：`@playwright/test`（Chromium 一套即可）。
2. 测试钩子（仅 DEV/测试构建暴露）：`window.__trainerChart` 暴露只读计数器（overlay 数量/选中集合/模式状态），供 journey 断言；生产构建不注入。
3. 隔离实例启动器：复用 verify-m2 模式（临时库+固定端口+环境变量），journey 前置全局 setup 自动拉起、teardown 关闭。
4. 失败自动附截图与 trace（Playwright 内建）。

### 维护成本控制

- Journey 只覆盖**最长手册路径 + 已知 failure pattern 的组合断言**，不做全分支穷举（组合空间由模式机互斥断言兜底）。
- 每步断言优先用测试钩子的状态断言（稳定），截图只做存档（不比对，避免 golden 维护成本）。
- 新工具/新模式合入时，journey 追加对应幕段——与"单功能验收闸门"流程天然契合：每个交付单元的提验前置跑一次 journey。

## 五、架构/lint 规则建议

1. **模式机集中化**：所有交互模式（default/画线/多选/轴拖拽/框选）的互斥关系已集中在 KlineChart 的事件入口守卫中；规则化——新增交互模式必须①挂到 onHostMouseDown/onPointerDown 的同一守卫链，②在 frontend-contract 增加互斥断言，③在本文件登记 failure pattern。
2. **库适配审查规则**：任何覆盖 klinecharts 样式/行为的代码，必须附带绘制源码依据注释（已有先例：priceMark 三键、bar 图元宽度），并在 frontend-contract 锁定该行为。
3. **监听器配对**：onMounted 注册的监听器必须在 onUnmounted 对称移除（现已有约定，可加 eslint 插件强制）。
4. **内部 API 钉定登记**：所有依赖 klinecharts 内部结构的写法（_chartStore.getLayoutOptions、setAutoCalcTickFlag、_event._handler）集中登记于 KlineChart.vue 头注释，升级时逐项复查。

## 六、实施计划（待批准）

| 步骤 | 内容 | 规模 |
|---|---|---|
| 1 | @playwright/test devDependency + 隔离实例启动器 + 测试钩子（DEV 构建注入） | 半天 |
| 2 | Journey 骨架：第 1 幕训练闭环 + 第 5 幕交易（复用 verify-m2 的断言逻辑） | 半天 |
| 3 | Journey 第 2/3/4/6 幕：画线全生命周期 + 交互矩阵 + 多选 + 主题 | 1 天 |
| 4 | npm run journey 脚本 + 提验流程纳入（每个交付单元提验前跑 journey） | 2 小时 |
| 5 | 库版本哨兵测试 + 本文件登记的规则落地检查 | 2 小时 |

总计约 2~2.5 天。完成后：每个交付单元的提验前置跑一次 journey，已知 60% 的 failure pattern（A+B）在提验前由真实事件自动化覆盖，用户验收从"第一道人工回归"变为"最后一道确认"。
