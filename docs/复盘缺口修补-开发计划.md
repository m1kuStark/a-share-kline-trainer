## 二、P0：复盘四缺口（均为 ≤2h 量级，快赢）

### G1 诊断信息（发布后可观测性）｜≤2h，唯一动产品码的 P0 项

- **前置实验 E1（10 分钟）**：确认桌面端日志是否落盘——在已安装机器（gpu3060 或本机）查 `<数据目录>/logs` 与 `%APPDATA%`；读 `desktop/src/main.ts` 的 `log(` 调用去向（复盘时未见 electron-log，**不确定**即以实验为准）。
- **动作**：
  1. E1 出结论。若不落盘 → 最小日志方案落 `<dataDir>/logs/main.log`（proposed_default：自写 append＋简单滚动，不引入 electron-log 新依赖；见拍板 8）。
  2. 设置页加「复制诊断信息」按钮：版本/平台/数据目录/更新状态/最近错误，**不含任何训练与交易数据**，一键复制到剪贴板。
- **矩阵**：`desktop-app.yaml` 加诊断按钮行为行；`updater.yaml` 加"更新状态可读"行。先加行（planned）再实现。
- **验收收据**：gpu3060 故意配错 TDX 目录，2 分钟内产出一份可直接贴 issue 的诊断文本；desktop vitest 全绿＋新增断言。
- **TDD**：按钮行为先 RED（复制内容包含哪些字段、绝不包含哪些字段——负向断言锁"不含训练数据"语义）。

### G2 release 资产核对｜~1h（脚本＋手册）

- **背景**：v1.3.1 误删事故（旧 416523806 → 重建 416593577）证明**人工上传是最后的高风险点**；"删除类操作实时核对目标"已入操作纪律，本条把**上传后核对**工具化。
- **动作**：
  1. `desktop/scripts/release-desktop.mjs` 产出资产 manifest（文件名＋大小＋sha256）。
  2. 新增核对脚本：对 GitHub release 与镜像 feed/ 双源核对——资产数量=期望值、SHA256SUMS 与实际资产一致、latest.yml 的 version/文件名/大小/sha512 一致、latest 指针指向预期 release。
  3. 写入 `docs/release/desktop-release-manual.md`（"发布后核对"一节，含**每轮发布后核验 latest 指针与各 release 状态**——第十/十一轮教训）。
- **验收收据**：对现有 v1.3.0/v1.3.1 跑核对得 7/7 双源一致；构造"少一项资产"场景时脚本报红（dry-run 模式验证）。

### G3 e2e 存量 93/125 三桶分类｜~2h（只分类，不清偿）

- **现状**：29 失败＋3 未跑，两轮一致（基线稳定，可分类）。
- **动作**：逐条归因三桶——**真 bug / spec 过时 / 环境依赖**；分类表回填 `docs/work-items/tasks/E2E-BASELINE-01.md`。
- **产出后走向**：
  - 真 bug 桶 → 逐条立卡，进 M2 清偿轮；
  - spec 过时桶 → 待拍板 5（更新 spec or 删用例）；
  - 环境依赖桶 → 登记 known/expected（符合 harness 红线：存量失败走登记、新失败阻断）。
- **同时回答复盘追问②**：这 29 条当前**不在任何必过门禁链上**（e2e 无 npm script、不进 CI 必过项）——这个事实本身要不要改，即拍板 6。
- **验收收据**：29＋3 条条有桶有归因注记；E2E-BASELINE-01 状态列更新。

### G4 SmartScreen／杀软用户指引｜~30min（纯文档）

- **动作**：`docs/user/troubleshooting.md` 补两段——① SmartScreen「更多信息→仍要运行」操作路径；② 杀软拦更新的自救（含 `.old` 已回滚场景：直接重新下载全量包覆盖安装）。
- 与 G1 互相引用：报障先贴「复制诊断信息」输出。
- **明确不做**：代码签名（复盘已定，成本档位不匹配；翻案另立卡）。
- **验收收据**：文档覆盖两大场景，`npm run docs:check` 过。

## 七、验收与证据通用要求

- 收据＝命令＋退出码；无收据的"完成"按未完成处理；存量失败走登记，新失败阻断。
